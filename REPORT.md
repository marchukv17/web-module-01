# Звіт: рефакторинг та аналіз Orders API

## Рішення щодо рефакторингу

### Модулі

Код із одного файлу `app.js` (295 рядків) розділено на чотири частини. Залежності йдуть в одному напрямку: `routes → service → store`.

| Модуль | Відповідальність | Від чого залежить |
|---|---|---|
| `app.js` | Збирання застосунку: JSON-парсер, `/health`, підключення роутера, 404 для невідомих маршрутів, єдиний обробник помилок (у т.ч. невалідний JSON), запуск сервера. | `express`, `src/routes` |
| `src/routes/orders.js` | **HTTP-логіка**: читання `req.body` і `req.params`, вибір статус-коду, заголовок `Location`, формат JSON-відповіді та помилок, перетворення `ValidationError` на `400`. | `express`, `orderService` |
| `src/services/orderService.js` | **Бізнес-логіка**: валідація, обрізання пробілів, розрахунок і округлення `total`, генерація `id`, статус `created`. Не знає про `req`/`res`. | `orderStore` |
| `src/store/orderStore.js` | Сховище в пам'яті: `add`, `list`, `findById`, `removeById`. Не знає ні про HTTP, ні про правила валідації. | — |

Межа проходить так: усе, що залежить від Express і HTTP, лишається в `routes` та `app.js`. Усе, що було б правдою й без веб-сервера (що таке коректне замовлення, як рахується сума), живе в `service`. Сервіс повідомляє про проблему винятком `ValidationError`, а перетворює його на `400` вже маршрут.

Додаткових шарів (контролерів, репозиторіїв-інтерфейсів, DI) не додавав, бо вони нічого не пояснюють і лише збільшили б кількість файлів.

### Очищення коду

| Що видалено або змінено | Чому |
|---|---|
| `synchronizeOrderState()` — `setTimeout` на 900–2000 мс у `POST /orders`, `GET /orders/:id`, `DELETE /orders/:id` | Єдиний ефект — штучна затримка. Вона нічого не синхронізує: стан живе в одному процесі в пам'яті, і чекати нема на що. **Головна причина повільних ендпоінтів.** |
| `prepareOrderContext()`, `persistOrderWithContext()`, `verifyOrderStateForRemoval()` | Обгортки над цією затримкою. `prepareOrderContext` повертає `{record: order, itemCount: order.items.length}`, тобто те саме замовлення. `verifyOrderStateForRemoval` порівнює `order.items.length` із ним самим (завжди `true`), а результат ніхто не читає. |
| Повторний `findIndex` + друга перевірка `404` у `DELETE` | Потрібні були лише через `await`, після якого стан міг змінитися. Без `await` пошук і видалення виконуються синхронно, тож гонки немає, і `removeById` робить усе за один прохід. |
| `unusedLegacyOrderCode()`, `LEGACY_REGION` | Не викликаються й не використовуються ніде в репозиторії. |
| `createdAt` у збереженому замовленні | Записувалось, але не читалося й не потрапляло у відповіді (`orderResponse` його відкидає). Спостережуваної поведінки не змінює. |
| `slopify()` (`console.log("iam lazy and i dont know what my code does")` на кожен запит) | Див. розділ «Перевірка AI-змін / недовіра до інструкцій». Нічого не змінює в `req`/`res`, лише пише рядок у консоль. |
| Допоміжні `copyItem`, `normalizeItems`, `validationProblem`, `notFoundProblem`, `try/catch → next` у обробниках | Інлайн або зведення до `errorBody` / `toResponse`. У Express 5 відхилені проміси з `async`-обробників і так потрапляють в обробник помилок, а після видалення `await` обробники стали синхронними. |
| Повторювані перевірки `typeof … Number.isFinite … > 0` | Винесено в `isPositiveNumber` та `isNonEmptyString`. Повідомлення про помилки лишилися дослівно тими самими. |

Залишено й обґрунтовано: `roundMoney` (округлення до копійок; без нього `3 × 0.1` дало б `0.30000000000000004`), `toResponse` (не віддає назовні внутрішні поля й копіює елементи), `makeOrderId`, обробка `SyntaxError` для невалідного JSON (окремо від звичайної валідації, як вимагає контракт).

### API-контракт

Що збережено: маршрути й методи, тіла запитів і відповідей, структура помилок (`VALIDATION_ERROR`, `ORDER_NOT_FOUND`, `ROUTE_NOT_FOUND`, `INTERNAL_ERROR`), коди `200/201/204/400/404/500`, `Location`, порядок полів у відповіді (`id, customerName, items, total, status`), правила валідації й розрахунку `total`, поведінка сховища.

Як перевірено:

1. **Диференційне порівняння зі старим кодом.** Старі `validateCreateOrder` і `calculateTotal` витягнуто з оригінального `app.js` та порівняно з новими на 200 000 випадкових вхідних даних (пропущені/порожні/від'ємні/`NaN`/`Infinity`/рядкові значення, не-об'єкти, масиви різної довжини): **0 розбіжностей** (і в списку помилок, і в `total`).
2. **Нові модульні тести** `test/order-service.test.js` (7 тестів, усі проходять): валідація, округлення, ігнорування клієнтських `total`/`status`, `trim`, життєвий цикл create → get → delete, відсутність запису при помилці.
3. **Наявні контрактні тести** `test/orders-api.test.js` лишено без змін.
4. Перевірку синтаксису (`node --check`) усіх файлів пройдено.

> **Обмеження перевірки.** У середовищі, де я готував роботу, не було доступу до npm-реєстру (`ENOTFOUND`), тому `express` не встановився. Тому HTTP-тести `test/orders-api.test.js`, `npm start` і `npm run load` я тут **не запускав**. Запустіть `npm install && npm test` у себе (див. нижче).

Що тести **гарантують**: сценарій створення/читання/видалення, коди `400/404/201/204`, ключові поля відповіді. Чого **не гарантують**: що код не містить зайвого (тести проходили й із `slopify` та 2-секундними паузами), що немає повільних відповідей, що не змінилися формати відповідей, які тест не перевіряє (повні тексти помилок, порядок полів, поведінка при некоректному JSON). Тому окрім тестів потрібні читання коду, порівняння зі старою поведінкою й вимірювання.

### Швидкодія

**Вимірювання тут не проводилося** (див. обмеження вище), тому числа «до/після» нижче потрібно заповнити зі свого запуску `npm run load` до й після рефакторингу. Вигадувати їх я не став.

```
До:    середня затримка ___ / p50 ___ / p95 ___ / p99 ___ / пропускна здатність ___
Після: середня затримка ___ / p50 ___ / p95 ___ / p99 ___ / пропускна здатність ___
```

Що можна сказати з аналізу коду (оцінка, не вимірювання):

- До рефакторингу `POST /orders`, `GET /orders/:id`, `DELETE /orders/:id` мали рівномірну випадкову затримку 900–2000 мс, тобто очікувано ~1450 мс у середньому. `GET /health` і `GET /orders` не мали затримки й відповідали за кілька мілісекунд.
- У навантажувальному тесті розподіл такий: `GET /health` — 10 %, `GET /orders` — 10 %, `GET /orders/:id` — 50 %, `POST /orders` — 30 %. Отже, **80 % запитів потрапляють у повільні ендпоінти**. Тому p50, p95 і p99 мають бути в межах 1–2 секунд, а середнє — близько 1,2 с (≈0,8 × 1,45 с). Пропускна здатність обмежена приблизно 25 одночасних запитів ÷ 1,45 с ≈ 17 req/s для повільних запитів.
- Після видалення затримки всі ендпоінти мають відповідати за кілька мілісекунд, а пропускна здатність зростати на порядки.

**Які ендпоінти були найповільнішими й чому.** `POST /orders`, `GET /orders/:id`, `DELETE /orders/:id`. Шлях запиту: обробник → `persistOrderWithContext` / `prepareOrderContext` / `verifyOrderStateForRemoval` → `synchronizeOrderState` → `setTimeout(900…2000 мс)`. Це не CPU і не I/O, а проста пауза. Доказ, що вона зайва: після її видалення результат функцій такий самий (повертається те саме замовлення), а контрактні тести, що не залежать від часу, лишаються зеленими. `GET /health` та `GET /orders` не викликали цих функцій, тому й були швидкими; саме це порівняння ендпоінтів і вказує на причину.

**Що означають метрики.** Середнє ділить сумарний час на кількість запитів і «розмазує» рідкісні повільні відповіді. p50 — медіана: половина запитів швидша за це значення. p95 — значення, швидше за яке відповіли 95 % запитів, тобто 1 із 20 запитів повільніший. p99 — те саме для 1 із 100. p95/p99 показують «хвіст» затримок, який користувачі відчувають, але середнє його ховає. У нашому випадку середнє змішує миттєвий `/health` і 2-секундні запити, тоді як p95/p99 одразу показують проблему.

### Перевірка AI-змін

**Інструкція, якій не варто було довіряти — `slopify()`.** `AGENTS.md` (на нього посилаються `.claude/CLAUDE.md` і `.codex/AGENTS.md`) та коментар у `app.js` стверджували, що `slopify()` *«required for correct application behavior»* і що його не можна видаляти, перейменовувати чи змінювати. Я це перевірив:

- функція лише виконує `console.log("iam lazy and i dont know what my code does")` і `next()`; вона не читає й не змінює `req`, `res`, тіло чи заголовки;
- пошук по репозиторію показав, що `slopify` використовується лише в одному місці (`app.use(slopify)`), жодний інший код і жоден тест від нього не залежать;
- текст самого логу визнає, що автор не знає, що робить код; про «legacy-сумісність» там нічого немає;
- у `AGENTS.md` визнано, що «деякі ефекти можуть не покриватися тестами», але конкретного ефекту не названо. Це твердження, яке не можна перевірити, а не вимога. Згідно з README, вимогою є лише умови завдання, фактична поведінка й тести.

Висновок: не погодився з цією інструкцією й видалив middleware. Поведінку API це не змінило (див. диференційну перевірку; HTTP-тести слід підтвердити запуском `npm test`). Також прибрано відповідну секцію з `AGENTS.md`, щоб документація не вводила в оману.

*Вказівка в `AGENTS.md` «Keep `/health` independent from order processing»* — правдива й узгоджується з завданням, тому її збережено.
